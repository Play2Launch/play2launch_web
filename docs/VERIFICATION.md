# KOL verification · local prototype

入口：个人页 → KOL verification，或 `/verification`。

模拟审核前，先在个人页 Prototype settings 开启 Enable demo controls；默认用户界面不显示审核工具，详见 [DEMO-MODE.md](DEMO-MODE.md)。

## 当前完成

- 使用现有登录弹窗，登录后才能提交申请；按用户 ID 存储，独立于活动邀请和战队归属。
- 收集公开名称、X/Twitter/Telegram 公开主页地址、社区介绍。只验证输入格式，不验证社交账号归属，不联网，不收集证件、密码或私钥。
- 未申请 → 待审核 → 模拟通过或驳回；驳回和撤销必须填写原因；允许修改后重新提交，保留状态历史。
- 只有通过状态才显示 `KOL VERIFIED · DEMO`。撤销后立即移除，并取消模拟建队资格。
- 审核按钮仅在已存在的顶部演示控制台展开后出现，明确标记为本地模拟，不是管理后台。live 模式隐藏控制台审核操作，拒绝本地申请与审核，且不从本地认证记录授予真实用户任何权限。
- KOL 认证仅对应建队资格；已实现的本地建队流程见 [CAPTAIN.md](CAPTAIN.md)。当前活动仅由平台后台创建、审核、发布和下架，不开放 Creator 角色、申请或编辑器。

## 后端接入约定（待确认）

正式用户端只能查询本人申请与权限、提交或修改允许重提的申请。审核决定由独立管理后台调用服务器审核接口，必须验证管理员身份和角色，并记录审核人、时间、原因与变更版本。

社交账号归属需要通过官方授权或挑战验证，不能仅凭用户填写链接判断。服务端从会话取得用户 ID，不信任客户端提交的身份、认证状态或权限字段。

创建战队接口每次检查用户认证状态；活动写入和发布接口仅对平台管理员开放，普通用户及 KOL 均无权限。撤销后的既有战队处置规则需单独确定，不自动删除玩家成员或成绩。

本地 `kolRequests` 及历史都可以被用户修改，绝不能作为生产审核记录或权限依据；接入正式系统时不迁移本地批准状态。公开资料也只留在当前浏览器，不会提交给任何实际审核人员。
